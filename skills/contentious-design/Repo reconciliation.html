Audit · contentiousltd/contentious-ui @ main

The repo knew more than you thought.

You said Contentious UI "isn’t visual and misses a lot of things". Half right. It has no visual layer and no product components – but its token foundation is more complete than this system’s was, and it already contains the score ramp I spent a turn reconstructing. Four token collisions would have broken this system inside an app; I’ve fixed those. Seven decisions are yours.

Fixed – collisions that would have broken things

These weren’t differences of opinion. Same token name, different value, silent breakage.

01

The score ramp already exists as --star-1..5

Aliased

I reconstructed the five-level ramp from the brand colour guide’s two "halfway between" notes. The repo has had it all along, with exactly the values I derived – and a getScoreColour(score, prefix) helper to go with it.

star-1
star-2
star-3
star-4
star-5

The repo’s names win – they’re in shipping code and in the product themes. --star-* is now primary here and --level-* is an alias, so nothing in this project breaks. New work uses --star-*.

Worth noting the prefix parameter: getScoreColour(3, 'maturity') gives var(--maturity-3). So the ramp is designed to be re-skinned per product, which is more thought than I’d credited it with – and something this system should document rather than hard-code.

02

--transition-fast means 300ms in the repo, 180ms here

Was broken
Repo (legacy Astro token)
--transition-fast: 300ms ease-in-out
--transition-base: 800ms ease-in-out
--transition-slow: 1.5s ease-in-out
This system, as authored
--transition-fast: 180ms ease
--transition-base: 280ms ease
--transition-slow: 500ms ease

This was a real bug, not a difference. Every hover, every switch, every menu in this system used var(--transition-fast). Dropped into an app, they’d have resolved to the repo’s 300ms and run 120ms slow – and --transition-base would have tripled to 800ms. Nothing would look obviously wrong; it would just feel sluggish, and nobody would find the cause.

The repo also has a proper motion scale that the legacy tokens predate: --duration-instant/fast/normal/slow/glacial at 100/200/350/500/800, exits at 75% of entrances, and three exponential easing curves. That’s better than what I had.

Fixed
This system now uses --motion-state, --motion-reveal and --motion-exit, which resolve through the repo’s duration and easing tokens with fallbacks. The colliding --transition-* declarations have been deleted, not just unused — so porting tokens/ cannot retime the Astro site in the opposite direction.

Your decisions

Six places where the repo and this system disagree and neither is obviously right.

04

The repo already ships Courier New as --font-mono

Escalated

Discrepancy 01 in the style-guide audit was framed as a proposal. It isn’t – src/styles/typography.css sets --font-mono: 'Courier New', monospace, so the brand’s code-only mono rule is already implemented in shipping code.

Which means the live app is in an odd position: its metadata labels are mono, but the token they’d resolve through is Courier. Either the app isn’t using --font-mono for labels (and has its own font stack somewhere), or those labels are already rendering in Courier and the screenshots are showing me that. Worth checking which.

Decision needed
Add a second token to the repo – --font-mono-ui or similar – for the metadata voice, distinct from Courier-for-code. That’s a small, additive change to the library and it makes the app’s existing practice legitimate. The alternative is rebuilding every label in Bely.
05

0–100 scores have no mapping anywhere

Real gap

getScoreColour takes a 1–5 score, not 0–100 – so criteria, which are scored in stars, are fully handled. But Watchlist’s score column and the headline gauge show 0–100, and nothing in the repo says how those band.

That explains the inconsistency the screen audit found: Watchlist invented a two-band threshold at 80 because there was no shared rule to follow. This is a genuine gap in the library, not something I duplicated.

Decision needed
Add scoreToStars(score) to src/lib/colors.ts beside getScoreColour, with the real framework boundaries. My provisional 90/80/70/60 is in --score-band-* here and should not ship as-is.
06

Base font size: 24px there, 19px here

Decide

The repo sets --base-font-size: 24px with a responsive --text-multiplier stepping 1 → 1.1 → 1.2 at 48rem and 96rem. So on a large screen the effective base is 28.8px.

You said the app’s type felt too small and I raised it from 15px to 16px. Against 24px scaling to 28.8px, 16px is still a long way off – which is probably why it kept feeling small: the app has been diverging from the brand base by more than a third.

Decision needed
The right answer is probably a documented app multiplier rather than a separate base – e.g. keep --base-font-size: 24px and set --text-multiplier: 0.75 for dense app screens, giving 18px that still scales with the brand. That keeps one system instead of two. Want me to work that through and show it at a few sizes?

09

Several components here duplicate shadcn ones there

Decide

The repo is shadcn-based and already exports Button, Badge, Card, Switch, Input, Select, Tabs, Tooltip, DropdownMenu, Progress, Table, Separator, Dialog and Toast – plus its own PageHeader, SectionHeader, Section, EmptyState, FeatureCard and LoadingRing.

So roughly half of what I built already exists. My Chip is its Badge; my Field is its Input/Select/Textarea; my Menu is its DropdownMenu; my SecondaryNav is its Tabs; my ProcessBar is its Progress. My PageHeader and SectionHeader collide by name with different implementations.

The value in what I built isn’t the components – it’s the rules attached to them. "Never full-radius on a label" is a fact about Badge. "Off must give up the fill" is a fact about Switch. Those belong on the repo’s existing components, not on parallel ones.

Recommendation
Don’t port the duplicates. Instead, write the .prompt.md rules against the repo’s existing components, and port only what genuinely doesn’t exist: StarRating, ScoreGauge, ScoreHistory, CriterionCard, ResultCard, Metric/MetricBand, CompositionBar, MicroSeries, ListRow, ProjectSwitcher, Breadcrumb, AppFooter. That’s twelve, not twenty-five.

Different tints and different geometry. Mine are tinted to gloaming, which sits better on limestone – a neutral black shadow on a warm cream surface reads slightly grey and cold. But the difference is subtle enough that it isn’t worth two scales.

Decision needed
I’d take the warm tint into the repo and keep the repo’s geometry. Small change, one scale, and shadows only appear on menus and tooltips so the risk is low.

What the repo is genuinely missing

You were right about this part. The foundation is strong; nothing sits on top of it.

MissingWhy it matters
Anything visualNo specimen cards, no rendered examples, no way to see a component before using it. docs/tokens.md lists names and values but you can’t look at them.
Usage rulesThe tokens are documented; the decisions aren’t. Nothing says solid fire means active and a fire tint means status, or that a score takes the star ramp while a quantity stays neutral. Every one of those has to be re-derived by whoever’s next.
Product componentsThe primitives are generic shadcn. Nothing knows what a criterion, a score, an estate or a watchlist is – so every product rebuilds them, differently.
The section illustrationsbrand/ holds product logos but not the estate / inventory / watchlist / results illustration set, which is the product’s strongest brand moment.
Semantic surface namesThemes map --background, --card, --muted per product, but nothing distinguishes a chrome surface from a data surface from a menu panel – which is how a slab ends up inside a slab.
Contrast floorsNothing records that gloaming-450 is the floor for small text, so --warning-text ships at sunshine-900 and every label is one careless edit from failing.

All six are things this system has. That’s the actual division of labour: the repo owns values and code, this owns meaning and appearance – and the .prompt.md files are the bridge, because they’re rules written where an agent will read them.

Order I’d do it in

1. Add the two missing tokens to the repo. --font-mono-ui and a scoreToStars mapping. Small, additive, and everything else depends on them.

2. Fix --warning-text. It fails contrast at small sizes today, in every app.

3. Settle the type scale. Probably an app --text-multiplier rather than a second base size – I’ll show you options.

4. Rename this system’s CSS to c-* and layer it. Then it can be ported as-is.

5. Write .prompt.md files against the repo’s existing components – Badge, Switch, Tabs, Input, DropdownMenu, Progress – rather than porting my duplicates.

6. Port the twelve components that genuinely don’t exist, starting with StarRating.

I can do 4, 5 and 6 as pull-request-ready files in the repo’s conventions. 1, 2 and 3 need your call first, because they change behaviour in every app that consumes the library.
