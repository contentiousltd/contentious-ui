# ADR-UI-0005: Shipping JavaScript to consumers

**Status:** Proposed
**Date:** 2026-08-03

## Context

This package ships **raw TypeScript** and is installed by git tag
(`github:contentiousltd/contentious-ui#v0.9.3`). `dist/` is gitignored, there is no build
step, and `main` / `module` / `types` are unset. `exports` points straight at source:

```json
".": "./src/index.ts"
```

That works for **CSS**, which is what the package is mostly used for today. Every consumer
imports `@contentious/ui/styles/*` and gets tokens, and the arrangement has been fine.

It does not work for **JavaScript**, and the cost has now been paid three times
independently.

### What it actually costs

**Content Health Check, 1 August 2026.** The server bundle is built with esbuild
`--packages=external`, so an `import` of `@contentious/ui/lib/colors` survives to runtime
as a request for a `.ts` file, which Node cannot execute. CHC could not import the
library's banding rule, so `shared/scoring.ts` **restates it**, with a parity test
asserting the copy still agrees with the original for every integer 0–100.

**Content Maturity, independently.** `client/src/lib/maturity-bands.ts` restates the same
rule again, and says why in its own words:

> *"The package exports `getScoreColour(score, prefix)` which does exactly this for a 1-5
> score. It is restated here rather than imported because nothing else in this app pulls
> JavaScript from the package yet, and adding the first import of its TypeScript source is
> a build-surface change rather than a colour one."*

That is a correct and careful decision. It is also the third copy.

**Verified identical.** `scoreToStars` in the library, `scoreToStars` in CHC's `shared/`,
and `maturityBand` in CM's `lib/` return the same level for every integer 0–100. Three
implementations, one rule, nothing keeping them in step.

### Why this matters more than it looks

The 30 July decision (ADR-UI-0004) settled that around twenty of the twenty-five specced
components are generic and belong to the suite. The library ships **seven**. `Button`,
`Card`, `Chip`, `Field`, `Metric`, `Tooltip` and the rest still live only in product
repos, in parallel copies.

The reason is not disagreement about what should be shared. **It is that a product cannot
reliably import JavaScript from this package**, so every shared component is unreachable
and each product writes its own. The packaging constraint is what is actually enforcing
the duplication that ADR-UI-0004 exists to remove.

There is direct evidence the shared path works when it is reachable: the `Switch` fix in
v0.9.3 (`transition-transform`, which Tailwind 4 made inert) was one change that corrected
every consuming product. Had each product kept its own switch, that would have been three
fixes and probably one forgotten.

## Decision

**Not yet made.** This ADR records the constraint and the options; the choice wants making
deliberately, since it sets the package's build surface for the whole suite.

## Options

### A. Ship compiled output, built on release

Restore a build (the vendored fork used `tsup` with `format: ['esm','cjs']`, `dts: true`,
peer deps external — that config is recoverable from `f56566a6^`). Point `exports` at
`dist/`, keep `./styles/*` pointing at source.

Because consumers install **from a git tag rather than a registry**, `dist/` must be
committed on the release commit, or generated by a `prepare` script that npm runs on git
installs.

- **For:** consumers import normally, no build-surface change in any product, types come
  with it.
- **Against:** committed build artefacts, or a `prepare` hook that must work in every
  consumer's CI (including CHC's `npm ci --include=dev` and CM's private-package auth).
  Release becomes a two-step: build, then tag.

### B. Publish to a registry

GitHub Packages or npm, private. Removes the git-tag constraint entirely and makes `dist/`
a normal artefact.

- **For:** the standard answer; version resolution stops being a git concern.
- **Against:** auth in every consumer's CI, and CM already carries a
  `private-packages-auth` action for exactly this kind of problem, which suggests it is
  not free.

### C. Consumers transpile the package

Keep shipping source; each product tells its bundler to process `@contentious/ui`.

- **For:** no change here at all.
- **Against:** pushes the cost onto every consumer, and **does not solve CHC's case** —
  the server build deliberately externalises `node_modules`, which is the reason its
  import failed. This option fixes clients only.

### D. Split what is importable from what is not

Ship the pure, dependency-free modules (`lib/colors.ts`, `types/`) as compiled JS, and
leave React components as source for client bundlers.

- **For:** unblocks the banding rule and the tokens, which is where the demonstrated
  duplication is, with the smallest build surface.
- **Against:** two rules for one package, and it defers the component question rather than
  answering it.

## Recommendation

**A or D**, and D is the cheaper first move because it targets the duplication that has
actually been observed three times, without committing the suite to a component build.

Whichever is chosen, the test is the same: **can CHC's server, built with esbuild
`--packages=external`, import `scoreToStars` and run?** If yes, `shared/scoring.ts` and
`maturity-bands.ts` both collapse into imports and the three copies become one.

## Consequences

**If solved.** The banding rule has one home. `ScoreGauge`, `ScoreValue` and `StarRating`
become genuinely shareable — and the evidence says they should be, since CM's maturity
model is also five levels on the same `--star-*` ramp with the same nearest-star rule. The
twenty generic components ADR-UI-0004 identified become reachable, one at a time.

**If not solved.** Every product keeps restating shared rules, each copy correct on the day
it is written. Today three copies of the banding rule agree exactly; there is no mechanism
that keeps them agreeing, and the failure is silent — a product renders a plausible wrong
level and nothing errors.

That is the same failure this package exists to prevent, one level up. Content Health
Check found **fourteen** copies of its own banding rule under **five** different answers on
1 August; the fix was one function and a test that fails the build on a second. This is
that problem across repositories, where a test in one repo cannot see the others.

## Notes

- `docs/design-system-sync.md` records that packaging is **"Claude Code's, never an
  export"**, so this is not a Claude Design question.
- The component question (which components move, and when) is downstream of this one and
  should not be answered first. A component nobody can import is not shared.
- Deliberately unaddressed here: whether the design system's `components.css` becomes the
  library's component layer. That collision is recorded as open in
  `design-system-sync.md` and is Claude Design's call, but a React component that needs
  those classes cannot ship until it is resolved.
