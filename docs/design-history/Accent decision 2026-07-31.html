Design brief answer · 31 July 2026

One accent, and it is the loud one.

Candidate 1. The design system keeps --accent; shadcn's pair is renamed to say what it is. The signature set grows by one — a hover step is a ground token, and it cannot be derived.

The decision

Three reasons, in the order they carried weight. The third is the one that settles it, and it is not about naming at all.

01

The dimension and the token have to share a name

accent is one of the six signature dimensions in products.css, alongside deployment, ground, illustration register, display presence and density. Under candidate 2 the dimension is still called accent and the token it sets is called --primary-action. Every product block would then read as a small translation exercise, and the layer's whole value is that a reviewer can see a signature at a glance.

Meaning A also owns a coherent family of five — --accent, -hover, -marker, -link, -link-hover — plus --focus-ring sitting in the same group. Meaning B is a pair. Rename the pair.

02

shadcn's --accent is the anomaly, not ours

In shadcn the loud interactive colour is --primary; --accent is a recessive hover surface. That is a local convention, and it is the opposite of what the word means in every brand vocabulary including this one, where the accent is the single colour the whole product is allowed to be loud in. Renaming the anomaly is the cheaper idea even where it is the more files.

You framed this as the .c-card precedent, and it holds: two things that were never dialects of one thing, named apart. But that precedent also decided which one moved — the borderless data surface kept .c-card because it is the one the system talks about constantly. Same test here.

03

The value is wrong too, and that is what makes it easy

The system already decided what a hover surface is. "Hover is a background step, not a colour shift" — a menu row or control goes transparent → --surface-raised, a list row to a lighter step. So --accent: sunshine-500 in the theme files is not only a name collision, it is a value that contradicts a settled rule: it paints hover in a brand colour, which is exactly the colour-shift the rule forbids.

Nobody has ever seen it. The bridge resolved bg-accent to fire-500, so meaning B was already losing before products.css existed. That means there is no shipping appearance to preserve on either side — the rename is not a migration, it is a correction that happens to need a new name. Fix both in one pass.

Decision
Candidate 1. --accent and its family stay as they are, in semantic.css and products.css. shadcn's --accent / --accent-foreground become --surface-hover / --text-on-hover, and take the system's hover value rather than sunshine-500.

Your question: does the closed set grow?

Yes, by one, and it goes in the ground group rather than the accent one. The first draft of this answer said no — that --surface-hover could alias --surface-raised, since every product already declares a raised step. That is wrong on half the suite, and wrong on precisely the products the argument leaned on.

04

Raised is a band. Hover is a step. Only CHC makes them coincide

Raised is a band — an aside block, a section of a marketing page, the seg-control track. Hover is a step off the surface being hovered. Two different jobs that happen to land on the same value in CHC, which is the ground this system was written against and the reason the conflation survived a first reading.

So it is declared, per product, and it is neutral: take the step from the family the menu and field surfaces are in, not the one the page bands in. On a dark ground it lightens.

/* products.css — the 29th token, ground group */
[data-product="chc"]         --surface-hover: var(--limestone-600);
[data-product="cm"]          --surface-hover: var(--limestone-600);   /* menus are limestone */
[data-product="vts"]         --surface-hover: var(--sorbet-750);      /* lightens off sorbet-800 */
[data-product="contentious"] --surface-hover: var(--limestone-600);   /* not the lichen band */
Decision
The set grows to 29. --surface-hover joins the ground group and every product declares it. --text-on-hover is not in the set — it equals --text-strong in every product and exists only so the shadcn codemod stays mechanical.

That is the third growth, and it has the same shape as the first two: a signature that could not describe a shipping product. --text-inset was VTS's light chrome over a dark page; --signature-deployment was the studio site's bands; this one is VTS again, plus the studio site.

What this asks of you

Theme filesTwo lines each in CHC and CM: --accent → --surface-hover, --accent-foreground → --text-on-hover. Drop the sunshine-500 value — products.css now declares --surface-hover per product. VTS and the website have no shadcn layer to change, but both take the new token like every other signature line.
ComponentsThe ten shadcn files per product, mechanically: bg-accent → bg-surface-hover, text-accent-foreground → text-on-hover, or whatever the Tailwind mapping names them. Find-and-replace, no judgement.
Import orderUnchanged and still matters: semantic.css before the theme file. With the collision gone, that is now a plain layering rule rather than a trap.
bg-accent/50Resolves itself. The opacity modifier was being dropped on a themed var(); at the hover step there is no half-opacity case left — a hover is one step or it is not a hover.

Found while answering

05

Two literal limestone stops in components.css break on a dark ground

.c-row:hover and .c-button--ghost:hover are var(--limestone-450) outright. On CHC, CM and the studio site that is correct and is the documented list-row step. On VTS it hovers a dark row to near-white. It has never shown, because VTS runs no design-system components yet — the same reason candidate 2 looked cheap.

Not folded into this decision, because fixing it properly means either a 29th token (--surface-hover-row, which every product would then declare) or deriving the row step from the card. That is a real argument and it deserves its own brief. Flagged so it is found before VTS adopts, not after.

Also, and separately

The typography.css split is done, in the same export as this answer. tokens/type-roles.css holds the roles and is importable on its own; tokens/semantic.css imports it itself, so --label-font-size and every --type-* shorthand now hold across the package boundary. tokens/typography.css keeps --base-font-size and --text-multiplier as prototyping defaults and every existing link is unchanged.

You were right to keep it out of this decision, and right that it is a defect rather than tidiness. It just turned out to cost nothing, so it did not need to wait its turn.
