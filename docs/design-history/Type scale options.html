Options · app type scale

One base, one multiplier.

The brand sets --base-font-size: 24px and scales the whole system from --text-multiplier, stepping 1 → 1.1 → 1.2. The app has been running a separate 15–16px base, diverging by more than a third – which is why the type kept feeling small no matter how I nudged it. Four options below, all rendered at real size on the same screen fragment.

Why a multiplier, not a second base

If the app declares its own base size, the two systems drift permanently: a change to the brand scale doesn’t reach the app, and every app screen has to be re-eyeballed. If the app instead sets a multiplier on the brand base, one number controls density and the relationship survives.

/* App theme — this is the whole change */
:root {
  /* --base-font-size stays 24px, from @contentious/ui */
  --text-multiplier: 0.75;   /* dense app screens */
}

Everything below derives from calc(var(--base-font-size) * var(--text-multiplier)) as one unit, then scales in multiples of it. Nothing is a hard-coded pixel value, which is the other half of the problem: the current system has ~60 literal font-size declarations, so "make it bigger" means editing sixty numbers.

Option D · responsive, 0.70 → 0.80

Follows the brand’s own stepping behaviour.

Worth adding later

The brand base steps at 48rem and 96rem. The app could do the same, one notch narrower: 0.70 below 48rem, 0.75 from 48rem, 0.80 from 96rem. On a 27-inch screen the app grows to 19.2px body without costing anything on a laptop.

@media (min-width: 48rem) { :root { --text-multiplier: 0.75; } }
@media (min-width: 96rem) { :root { --text-multiplier: 0.80; } }

Note what the "Now" column shows: the current scale isn’t proportional to anything. The page title is relatively larger than the brand ratio while the metric value is relatively smaller, because I set each number by eye. Deriving them from one unit fixes that as a side effect – the ratios become consistent, not just the sizes.

Recommendation

Option B, 0.75. Body 18px, mono labels clear of the floor at 11.2px, tables still fit, and it explains itself in one sentence: the app runs at three-quarters of brand size.

Add Option D’s steps in a fortnight, once 0.75 has proved itself as the middle. Not before – you want to be adjusting around a number you trust.

The real work isn’t the number. It’s replacing ~60 hard-coded font-size declarations in components/components.css with multiples of one unit. That’s what makes the next adjustment a one-line change instead of another sixty-number pass, and it should happen at the same time as the c-* rename so the CSS is only rewritten once.

One thing to check before committing: the repo’s --text-multiplier is currently used by type-h1, type-body and friends. If any app screen already uses those classes, changing the multiplier will move them too – which is the point, but worth knowing rather than discovering.
